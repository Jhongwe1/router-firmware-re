# The loader's interrupts, and the prompt that is not a prompt

Answers **open questions 101 and 102**, both carried from 2026-08-22. They turn
out to be the same question asked from two sides — *what runs the loader's
network, and what does the command prompt actually do while it is waiting?* —
and one reading settles both.

**Measured on:** `$FWRE_WORK/stage2.bin`, 56,592 bytes, the LZMA second stage
decompressed out of flash `0x0012F0` by `tools/loader-unpack.py` from
`dumps/flash-n150rt-console-2.bin`. Linked at `0x80400000`, so file offset =
address − `0x80400000`. Report:
[`reports/bootloader-unit-2018.json`](../reports/bootloader-unit-2018.json)
§`interrupt_wiring`, regenerated by `tools/loader-unpack.py <dump> --irq`.
The console evidence is `dumps/uart-boot.log` and `dumps/uart-bootloader.log`,
both captured 2026-08-16, and `$FWRE_WORK/dumps/w08-a28.log` from 2026-08-21.

---

## 101 — the answer

**The loader's TFTP is interrupt-driven, and `J` masking interrupts is by itself
enough to stop it.** Four legs, none of which shares a mechanism with another:

| | |
|---|---|
| **The prompt polls nothing but the UART** | `0x80406BBC` is the command loop's character source and it is an unbounded spin on the UART line status register: `lbu` from `0xB8002014`, `andi 1`, branch back. The only two addresses the whole routine touches are `0xB8002014` and `0xB8002000`, with **zero** unresolved memory references. While the board sits at `<RealTek>` nothing in the command loop looks at the network |
| **An `eth0` interrupt is installed** | `request_IRQ(15, 0x8040D6EC, 0x8040E9D0)` at `0x80402A44`. The irqaction's handler is `0x804023B0` and the name string it carries is literally `eth0`. Two more are installed the same way: IRQ 8 `timer` (`0x80408FEC`) and IRQ 27 `SPEED` (`0x8040A3C0`) |
| **Interrupts are enabled before the prompt is ever printed** | `0x80408468` calls the ethernet init `0x804028B4`, prints `\n---Ethernet init Okay!\n`, executes `mfc0 $1,$12 / ori $1,0x1f / xori $1,0x1e / mtc0 $1,$12` at `0x80408484`–`0x80408494` — which sets Status bit 0 — then calls the TFTP init `0x80401D18` and finally the command loop at `0x80409144`. **That console line is in this unit's own boot capture**, `dumps/uart-bootloader.log`, one line above the first `<RealTek>` |
| **The `eth0` handler is the packet input path** | `0x804023B0` acknowledges the MAC's interrupt at `0xB801002C`, then loops on `0x80403AB8` dequeuing frames and calling `0x80402040` for each. `0x80402040` dispatches on EtherType — `0x0800` and `0x0806` — into the IP and ARP paths that reach the TFTP service |

So the sequence that produced 2026-08-22's unattributable result reads like
this. `J` at `0x8040925C` writes `0` to `GIMR0` (`0x804092AC`), clears `IE`
(`0x804092B0`–`0x804092C0`), clears `EnablePHYIf` in `PCRP0`–`PCRP4`
(`0x804092F4`–`0x80409354`), flushes the caches and calls the payload. Restoring
the five PHY bits afterwards puts the wire back and **nothing dispatches what
arrives on it**, because the interrupt that used to is masked twice over.

### What the loader's own boot decides

```
                 0x8040868C  (the escape window)
                        |
        ESC not seen ---+--- ESC seen, or nothing to boot
              |                          |
   0x804084B8 boot the image     printf "---Escape booting by user"
   GIMR0 = 0, cli, cache flush,          |
   jump — never returns             GIMR0 = 0   (0x804086E4 / 0x80408700)
                                         |
                              0x80408468:
                                jal 0x804028B4   ethernet init
                                                 -> request_IRQ(15,"eth0")
                                                 -> GIMR0 |= 1<<15
                                printf "---Ethernet init Okay!"
                                sti                (0x80408494, sets IE)
                                jal 0x80401D18     TFTP service, default IP
                                                   192.168.1.6 (0x80401D1C)
                                jal 0x80409144     "<RealTek>" + GetLine
```

Two consequences worth stating separately:

* **`dumps/uart-boot.log` — an uninterrupted boot — contains no
  `---Ethernet init Okay!`.** The banner goes straight to
  `Jump to image start=0x80500000`. So the loader's network stack does not exist
  during a boot nobody interrupts, which is `P9-4`'s conclusion with an
  instruction-level argument behind it rather than only a passive capture.
* **`P9-4`'s recorded result says the stack "exists only after a serial
  IPCONFIG", and that is not what the code says.** It exists as soon as the
  escape window is taken, at the compiled-in `192.168.1.6`. `IPCONFIG`'s handler
  (`0x80409378`) parses a dotted quad into `0x8040EDC0` and does nothing else —
  it changes the address the stack answers on, it does not bring the stack up.
  The row's *conclusion* survives untouched; the sentence explaining it does
  not, and the correction is in `PROGRESS.md § Corrections` rather than edited
  into the register.

### The predicted value of `GIMR0` at the prompt, and the bit this reading cannot place

Every write to `GIMR0` in the image, in the order the boot takes them:

| where | what |
|---|---|
| `0x8040A318` / `0x8040A328` | the `SPEED` init sets bit 27, and `0x8040A4B0` **writes back the value it saved** at `0x8040A394` — so it leaves `GIMR0` as it found it |
| `0x80408FEC` | `request_IRQ(8, "timer")` sets bit 8 |
| `0x804086E4` / `0x80408700` | **`GIMR0 = 0`** on both paths into the monitor — the timer bit does not survive this |
| `0x80402FB8` | `GIMR0 |= 0x100` inside `0x80402F80`, in the switch/PHY driver |
| `0x80402A44` | `request_IRQ(15, "eth0")` sets bit 15 |

So bit 15 is decided and bit 27 is decided. **Bit 8 is not**: whether
`0x80402F80` is on the path from `0x804028B4` is a call-graph question this
reading did not settle, and `0x80402FB8` would set the same bit the timer uses.
`P9-18` therefore predicts **bit 15 set, bit 27 clear, bit 8 undecided**, and
names `0x80402FB8` as the instruction the measurement will settle. A prediction
that says which of its bits are load-bearing is worth more than a confident
32-bit number that might be wrong for a reason nobody wrote down.

### What the loader cannot do, and why that made the experiment expensive

There is **no command that writes CP0 Status**. `MTC0SR` is commented out of the
vendor's own table and is absent from the seventeen this build prints. So
re-enabling interrupts after a `J` needs a RAM payload — and `P9-16` had just
shown, on this unit, that a payload ending in `jr ra` comes back to the prompt.
`tools/mkramboot.py --irq-restore` builds it; the five instructions that set
`IE` are **copied word for word out of the loader's own `sti`** at
`0x80408484`–`0x80408494`, so the payload cannot restore a different interrupt
state from the one the prompt normally runs in.

## 102 — the answer, and it was on disk

**A clean `EB` line was rejected because eight spaces were already in the line
buffer, and the prompt that appeared to invite the command had been painted by
the TFTP completion path from inside the interrupt handler.**

Four facts, each checkable:

1. **The TFTP completion path prints a prompt.** `0x80401CD0` prints
   `"\n.Success!\n%s"` (`0x8040A948`) and passes `0x8040A894` — which is a
   **second copy of the string `<RealTek>`**. The upload path does the same at
   `0x80401AEC`, and so do the auto-burn write messages at `0x804018D0` and
   `0x804018B8`. All four run in the `eth0` interrupt handler.
   *This is why the mechanism was invisible for a day*: the obvious check —
   cross-references to the prompt string at `0x8040B314` — finds exactly one,
   the dispatcher's own `printf` at `0x80409178`, and says the prompt has a
   single owner.
2. **That prompt does not clear anything.** `GetLine` is still collecting a line
   in the main context; the interrupt wrote to the UART and returned.
3. **The buffer held eight spaces**, and the log shows them: in
   `$FWRE_WORK/dumps/w08-a28.log` the prompt before the TFTP output is followed
   by exactly eight echoed spaces. `stage2.bin` contains **no run of eight
   spaces anywhere**, so no `printf` can have produced them; `GetLine`'s only
   multi-space emitter is its TAB expansion at `0x8040713C`–`0x80407168`, which
   writes exactly eight. **Which key produced them is not decided**: one TAB and
   eight spacebars are indistinguishable in the echo, and both leave the same
   buffer. The cause of the rejection is settled; the keystroke is not.
4. **A line beginning with whitespace has `argv[0] == ""`.** The tokeniser at
   `0x80407248` stores `argv[i] = p` at `0x80407290` **before** testing whether
   `*p` is a space, then writes the NUL at `0x804072D4`. So `argv[0]` is the
   empty string, it matches none of the seventeen names, and the loader answers
   `Unknown command !` to a line that reads perfectly.

The log's own next two lines confirm the model: one Enter produced a prompt with
**no** complaint — an empty line takes `blez s4` at `0x804091C8` and reprints
the prompt silently — and the identical `EB` then worked.

### What the TFTP receive path can and cannot write

`102` asked whether the TFTP path can reach the monitor's line buffer or the
`argv` array at `0x8040EAE0`. Measured, and the answer is **not the way that
mattered here**:

* The payload of an incoming transfer goes to `[0x8040DD10]`, seeded from the
  TFTP load address `[0x8040D3A8]` at `0x80401268` and advanced linearly. There
  is **no end-address check anywhere on that path**, so with `LOADADDR` pointed
  into `.bss` it certainly can reach `0x8040EAE0` — and with the
  `boot.img` / `nfjrom` filenames, which force the load address to `0x80000000`
  (`0x80401258`), a transfer longer than about 4.2 MB would walk through the
  loader's own image and into its globals. That is a property of a recovery
  mechanism designed to hand control to what it receives, and it is not
  interesting on its own.
* The `probe` that preceded the failing `EB` was a **read** request that served
  **zero** bytes. It wrote nothing to RAM at all. So the write path is excluded
  as the cause, by the packet as well as by the code.
* The monitor's line buffer is not in `.bss`: it is `sp+16` in `0x80409144`'s
  frame, 128 bytes (`0x80409194` `li a2,128` for the `memset`, `0x8040919C`
  `li a1,128` for `GetLine`), with the stack top at `0x80421C34`.

**The filename is a different matter.** `0x804011FC` prints it with `%s`
straight out of the packet buffer, and the request is length-checked only at 42
bytes minimum (`0x80402068`). A TFTP request can therefore put arbitrary
non-NUL bytes on the operator's console, and one with no NUL terminator will
print whatever follows it in the receive buffer. It requires the escape window
to have been caught first — the stack does not exist otherwise — so it crosses
no privilege boundary this project has not already crossed with a UART cable.
It is recorded because the operator's console is a trusted display and this is
attacker-controlled text on it, and because it is the same shape as the prompt
repaint: **the console shows what the network asked it to show.**

### Two loader limits that bite at the bench and are not in any help text

* **`GetLine` takes 128 characters** and silently stops (`0x8040719C` is reached
  by the count test at `0x80407190`, not by an error). A longer line loses its
  tail with no message.
* **The tokeniser has twenty `argv` slots** (`0x8040728C` `li a1,20`, and the
  `memset` at `0x80407270` is 80 bytes). So an `EW` line carries at most
  eighteen values.

Both are enforced by `tools/mkramboot.py`'s `ew_lines()`, which refuses to emit
a line that would be truncated — because a payload written half-way is a `J`
into whatever was there before.

### And one that makes the whole command set friendlier than it looks

`0x804091D4` calls `0x80407040` on `argv[0]` before the comparisons, and
`0x80407040` is `strupr`: it upper-cases `a`–`z` in place. **The seventeen
commands are case-insensitive.** `help` still fails, because the table's entry
is `?` and `HELP` is only in the help text — which is exactly what
`dumps/uart-bootloader.log` shows on 2026-08-16.

## The rule this replaces

The operational rule written on 2026-08-22 was *"press Enter before typing
whenever anything has printed since the last prompt."* That is still good advice
and it is now the wrong shape, because it asks the operator to remember
something. The accurate rule is narrower and mechanical:

> **A `<RealTek>` that follows `Success!`, `.Success!`, `Flash Write Successed!`
> or `Flash Write Failed!` was printed by the interrupt handler. It is not a
> prompt. The line buffer behind it is whatever it was.**

and it is enforced rather than remembered: `tools/console-lint.py` reads a
`picocom` log the way the dispatcher reads it, classifies every prompt,
reconstructs the line buffer across repaints, and **accounts for every
`Unknown command !` in the file or reports it as unexplained**. Run on the two
logs that produced this note it explains both incidents, and on the W02 boot
capture it explains three more that nobody had asked about: the `Unknown
command !` bursts at the start of every escape-caught session are
`console-dump.py`'s own ESC stream landing in `argv[0]`.

## What this is, and what it is not

* **Two readers, not one.** The addresses above come from
  `mips-linux-gnu-objdump` over `stage2.bin` *and* from
  `tools/loader-unpack.py --irq`, which has its own decoder and does not call
  objdump. Where they disagreed the tool was wrong twice and both are recorded
  below. The `eth0` install has a third source: this unit's own boot log carries
  the console line the code prints one instruction before it enables interrupts.
* **This was measured on 2026-08-22**, and the section below says exactly which
  sentences the device confirmed, which it refuted, and which are still only a
  reading. `P9-17`, `P9-18` and `P9-19` all closed **`partial`**.
* **Still not confirmed, and it was the thing this note most wanted:** that the
  `eth0` ISR is what carries a *TFTP* packet. The bench showed the ISR carrying
  an **ARP** packet — request in, reply out, 0.9 ms, on a capture — and the TFTP
  path staying silent in the same state. The call-graph reading from
  `0x804023B0` to the TFTP handler still has **no device observable behind it**,
  and the measurement that was supposed to supply one came back negative.
* **Nothing here touches the auto-burn path**, which nothing in this note sends.

**`IRR3` is the one to read twice.** It carried a prediction and **no refutation
branch**, so it can be recorded and cannot be scored. Until somebody settles
whether `0x8040A398` was misread or simply never runs on this path, the
`installs` table claims only that the structure it found *resembles* an
irqaction. That is open item 105.

### The interrupt was proved by an event nobody designed

The strongest evidence for *"the receive path is interrupt-driven and `J` masks
it"* is not in the table. A payload that restored `GIMR0` **and left `IE`
clear** was jumped to, and TFTP stayed dead. A second payload differing in
**five words** set `IE` as well — and the instant it did, the console printed

```text
File Start: 80500000,length=00000000
**TFTP GET File probe,Size 00000000 Byte
```

**with no request having been sent.** That was the *first* payload's timed-out
request, held in the receive path with the interrupt pending and masked, taken
the moment `IE` went to 1. `0xB8003004` witnessed the same event independently:
`88000004` before any jump, `88000104` after the first, `88000004` after the
second.

### And what it did not bring back

TFTP. With `GIMR0` and `IE` both restored, a capture shows the loader answering
ARP in 0.9 ms and ignoring three TFTP read requests, console silent. So `IE` is
what packet **reception** was missing — and the service above it does not
recover. Two readings agree on why, and neither is a measurement: the transfer
taken at the moment `IE` rose printed its spinner and **no `Success!` line**,
where a healthy transaction prints two, and `console-lint` independently
classified the prompt after it as a command-loop prompt rather than a TFTP
repaint — counting exactly one repaint in the whole log, and it was elsewhere.
**The transfer started and never finished.** That is a candidate. Open item 103
is where it goes, and settling it means reading the TFTP state machine, not
returning to the bench.

## How the first version of this was wrong

**Version 1 concluded that the loader never enables interrupts at all, and it
was one `grep` away from being published.**

It searched for Realtek's `sti` idiom — `mfc0 $1,$12 / ori $1,1 / mtc0 $1,$12` —
found none, found seven `cli` sites of the matching shape, and read that as "the
loader runs with interrupts masked, so its TFTP must be polled." Every step of
that is a correct observation. The conclusion is the opposite of the truth,
because **this build writes `ori $1,0x1f / xori $1,0x1e`** — which sets bit 0
and clears bits 1 to 4 — and a search for one shape cannot see another shape
with the same effect.

What caught it was reading *every* `mtc0 $12` in the image instead of the ones
that matched, and computing bit 0 rather than recognising a pattern. That is now
what the instrument does: a four-valued per-bit lattice — `0`, `1`, *what `mfc0`
read*, *its complement* — so `xori` is exact and the answer is arithmetic.
`tools/test-loader-unpack.sh` holds it to that with two fixtures that differ in
**one bit of one immediate**: `xori 0x1e` must read as setting IE and
`xori 0x1f` must read as clearing it.

**A second way, and it is the same lesson in the other direction.** Version 1 of
the analysis located function entries by scanning backwards for `jr ra` and
taking the word after its delay slot. That is a reasonable rule and it is wrong
here: the routine before `enable_irq` ends in `rfe`, not `jr ra`, so the scan
ran past it and reported an entry address nothing in the image calls — and the
tool refused, loudly, with *"the GIMR0 bit-setter has 0 callers"*. It could just
as easily have landed on a real function and reported a confident wrong answer.
A function entry is not "after the previous return"; it is **an address a `jal`
names**, and this image names all of them.

**A third, and it is not about the disassembly.** The reason `102` sat open for
a day is that the search for who prints `<RealTek>` was a cross-reference search
on one address. It returned one result, the result was correct, and the
conclusion drawn from it — *the prompt has one owner* — was false, because the
same string is in the image **twice**. A cross-reference search answers "who
uses this address", and the question was "who prints this text".
