# Sink inventory — where user input can reach a shell or a fixed buffer

Generated by [`BoaSinks.java`](../ghidra/scripts/BoaSinks.java) into
[`reports/ghidra-sinks-2.1.2.json`](../reports/ghidra-sinks-2.1.2.json) and
[`reports/ghidra-sinks-3.4.0.json`](../reports/ghidra-sinks-3.4.0.json), then
read by hand. The script finds call sites; it does not decide whether any of
them is reachable with attacker data. Everything ranked below was read.

> **Static only.** No device has been powered on. "Reachable unauthenticated"
> throughout means *as the code reads* — see the scope note in
> [`auth-flow.md`](auth-flow.md).

### The first version of this table was wrong, and how that was caught

The first run reported **589** `strcpy` call sites in V2.1.2 and **1** in
V3.4.0, and would have supported a confident sentence about the 2020 build
having eliminated unbounded string copies. `nm -D` shows V3.4.0 importing
`strcpy`. One of the two was lying.

The cause is in the ELF, and it is the same shape as W01's `readelf` failure:

| | V2.1.2 | V3.4.0 |
|---|---|---|
| section headers | 29 | **none** (`sstrip`'d) |
| `DT_MIPS_PLTGOT` | absent | `0x472ac4` — a real PLT |
| how a caller reaches `strcpy` | thunk Ghidra named `strcpy` | `jal` to an unnamed PLT stub |

With no section headers Ghidra cannot find `.plt` to label its entries, and it
only turned *some* of them into functions — `system` and `sprintf` got one,
`strcpy` and `strcat` did not. Counting references to the symbol therefore
counted the GOT relocation and nothing else.

The fix does not guess. A MIPS PLT entry for `.got.plt` slot `S` is four
instructions whose every field is determined by `S`:

```
lui   $15, %hi(S)        3C 0F hi
lw    $25, %lo(S)($15)   8D F9 lo
addiu $24, $15, %lo(S)   25 F8 lo
jr    $25                03 20 00 08
```

so the stub is *constructed* and then required to exist at exactly one address.
Measured beforehand: `jal = 9979`, `jalr = 16` — essentially every call in this
binary is a direct jump to a PLT stub, which is why this works and why a
`gp`-relative approach was not needed.

Two changes went in alongside it, both about honesty rather than coverage:

- A data reference from **outside any function** is a GOT slot, not a call site.
  Counting it is exactly how `strcpy` came back as "1" instead of the truthful
  "0, and 0 is wrong".
- The report now carries a `self_check` field listing any sink the binary
  imports but that appears to have no callers, and marks the whole file
  `SUSPECT` when the list is non-empty. Both files currently read `consistent`.

**The lesson is W01's, twice over: a tool reporting zero has made a claim, and
it needs the same scrutiny as any other claim.**

## Ranked findings

Ranking: *reachability × attacker control of the bytes × absence of a check*.
Boa runs as root, and W01 established no canary, no RELRO, no PIE, no FORTIFY
and an executable stack on most binaries — so the exploitation cost of a stack
overflow here is low and constant, and reachability decides.

### 1. 🔴 `formWsc` — `peerPin` and `localPin` into `system()`, unfiltered

`/boafrm/formWsc`, handler `0x0044a190` (V2.1.2) / `0x0043f318` (V3.4.0).
Fourteen `system()` call sites in 2015, fifteen in 2020.

```c
/* V2.1.2, from the decompiled handler */
pcVar3 = req_get_cstream_var(param_1, "localPin", "");
if (*pcVar3 != '\0') {
    sprintf(acStack_220, "flash set HW_WLAN0_WSC_PIN %s", pcVar3);   /* acStack_220[100] */
    system(acStack_220);                                             /* @0x0044aa34 */
}
```

`localPin` is taken straight from the request and interpolated into a shell
command with **no length check and no character filter**. Two bugs on one line:

- **Command injection** — no metacharacter filtering at all.
- **Stack overflow** — the destination is 100 bytes and the format contributes
  27, leaving ~72 for a parameter of unbounded length.

The same parameter name is what CVE-2025-4462 names for this handler family on
sibling models. Present here, identically, in **both** builds:
V3.4.0 `sprintf(auStack_214, "flash set HW_WLAN0_WSC_PIN %s", localPin)` —
same 100-byte buffer, same absence of checks, five years later.

`peerPin` reaches `system()` down a second path:

```c
pcVar3 = req_get_cstream_var(param_1, "peerPin", "");
...
if (mib_0x10e == 0) {
    /* digits are extracted one at a time into local_254[52] … */
    while (uVar8 < strlen(pcVar3)) {
        if ((byte)(*pcVar4 - 0x30U) < 10) { local_254[iVar6] = *pcVar4; iVar6++; }
        uVar8++;
    }                                        /* <- iVar6 has no upper bound */
    sprintf(acStack_1bc, "iwpriv %s set_mib pin=%s", WLAN_IF, local_254);
    system(acStack_1bc);                     /* @0x0044a454 */
} else {
    sprintf(acStack_1bc, "echo %s > /var/wps_peer_pin", pcVar3);   /* raw */
    system(acStack_1bc);                     /* @0x0044a758 */
}
```

Both branches are wrong, in different ways, and the difference is instructive:

- The **filtered** branch is digits-only, so it is injection-proof — and then
  copies an unbounded number of those digits into `local_254[52]` with no cap on
  the index. A long numeric `peerPin` is a clean stack overflow, and the
  filtering is what makes it look safe.
- The **unfiltered** branch puts the raw parameter into `system()`.

### 2. 🔴 `formWsc` — `targetAPSsid` inside shell double-quotes

```c
if (*pcVar4 != '\0') {                       /* pcVar4 = targetAPSsid */
    if (strlen(pcVar4) < 0x21) {             /* length IS checked */
        sprintf(pcVar3, "iwpriv wlan%d set_mib wsc_specssid=\"%s\" ", _wlan_idx, pcVar4);
        pcVar9 = system;
    } else { pcVar9 = puts; pcVar3 = "invaild SSID Len"; }
    (*pcVar9)(pcVar3);
}
```

This is CVE-2025-6299's parameter, and the root cause is precise: the length
**is** bounded (< 33), so there is no overflow — but the value is interpolated
inside double quotes with no escaping, so `a";reboot;"` closes the quote and
appends a command.

The contrast with its neighbour is the finding. `targetAPMac`, ten lines earlier
in the same function, is filtered to `[0-9a-fA-F]` character by character *and*
required to be exactly 12 long. The developer knew how to sanitise; the
sanitisation is per-parameter and inconsistent. That is the signature of ad-hoc
input handling rather than a missing library.

### 3. ⚪ `execl` in six handlers — traced, and it is a negative result

`formDMZ`, `formFilter`, `formIpQoS`, `formPortFw`, `formSpiFwall`, `formRadvd`
each reach `execl` (eight handlers in V3.4.0). The first version of this entry
said "the argument vectors are built from request parameters (`comment`,
`ipStart`, `fromPort`, …)". **They are not.** Every `execl` site in both builds:

| build | handler | site | argv |
|---|---|---|---|
| 2.1.2 | formSpiFwall | `0x0041d228` | `(path, "firewall.sh", NULL)` |
| 2.1.2 | formDMZ | `0x0041d56c` | `(path, "firewall.sh", NULL)` |
| 2.1.2 | formFilter | `0x0041e5c0` | `(path, "firewall.sh", NULL)` |
| 2.1.2 | formPortFw | `0x0041cf88` | `(path, "firewall.sh", NULL)` |
| 2.1.2 | formIpQoS | `0x0041f328` | `(path, "ip_qos.sh", NULL)` |
| 2.1.2 | formRadvd | `0x0045e724` | `(path, "radvd.sh", NULL)` |
| 3.4.0 | +formAlgSip, +formNtp, +formRebootSchedule | | `(path, "<script>.sh", NULL)` |

A literal script name and a NULL. **No request parameter is passed to any
`execl` in either build.** The parameters go into the MIB; the shell script reads
them back afterwards. That is still a data flow worth following — a MIB value
interpolated by `/etc/scripts/firewall.sh` is the same bug one process later —
but it is not an `execl` argv problem and this entry was pointing at the wrong
thing. **Reading those shell scripts is W07.**

Bound on the claim: the tracer resolves the *arguments at the call*, and
`argv[0]` is a stack buffer holding the script path. It does not follow what was
written into that buffer earlier. So "no request parameter reaches argv" is
established for the argument slots, not for the path.

### 4. ⚪ Unbounded `strcpy` of the request URI on the 401 path — measured, downgraded

```c
strcpy(&DAT_0048e9f8, (char *)(param_1 + 0x235));   /* the request URI */
```

Both halves of the W03 open question are now answered, and they point opposite
ways.

**The ordering claim was wrong.** `translate_uri`'s `0x801` cap does *not* run
first: the `strcpy` is at `0x0040c378` and `translate_uri` is called at
`0x0040c3a8`, on the other branch. Nothing between the URI arriving and this copy
bounds it here.

**The impact claim was also wrong, in the other direction.** `DAT_0048e9f8` has
no symbol — it is a file-local static that stripping removed. The next *named*
global above it is `max_fd` at `0x0048faa0`, so there are **4,264 bytes** of
unnamed `.bss` between the destination and anything with a name, and Boa's own
request line is bounded well below that. A copy that cannot reach the next object
is not an overflow.

Downgraded from 🟠 to a non-finding. Kept in place because the reasoning that
produced the original rating — "unbounded `strcpy`, pre-auth, therefore
interesting" — is the reasoning that produced entry 1, which *is* interesting,
and the difference between the two is a number nobody had looked up.

Also measured, and mildly surprising: **`DAT_0048e9f8` is never read.** Its
address is taken exactly once in the whole binary, at `0x0040c378` — confirmed
both by Ghidra and by scanning the raw ELF for any load or `addiu` bearing the
displacement `0xe9f8`. The same scan shows `DAT_0048e9e8`, the other global this
function writes, has exactly one access and it is a store. Two write-only
globals in the authorisation path.

### 5. 🟡 The 47 handlers containing `strcpy`

Forty-seven of the 59 V2.1.2 handlers contain at least one `strcpy`. Most will
be copying MIB values into local buffers, which is uninteresting. Triaging them
means asking, per call, whether the source is a `req_get_cstream_var` return —
and that is the shape of a W07 systematic hunt, not something to eyeball now.
The full list is in the JSON.

### 6. ⚪ `formSaveConfig` — W01's top candidate, disproved

W01 called `FUN_00440eec` in V3.4.0 "the highest-value single function found in
W01" because it holds `cp /var/web/config.dat %s`. It is
`/boafrm/formSaveConfig`, and the `%s` is:

```c
sprintf(auStack_148, "/var/web/Config_%s_%04d%02d%02d%02d%02d%02d.bin",
        "N150RT", tm->tm_year + 0x76c, tm->tm_mon + 1, tm->tm_mday,
        tm->tm_hour, tm->tm_min, tm->tm_sec);
...
sprintf(auStack_1ac, "cp /var/web/config.dat %s", auStack_148);
system(auStack_1ac);
```

A literal model name and six `localtime()` fields. **No request data reaches it —
not a command injection.** Recorded because a candidate that dies deserves the
same visibility as one that survives; the alternative is a project where only
confirmations get written down.

The loose end is closed, and it was the decompiler. Ghidra's *inferred* frame put
8 bytes between `auStack_148` and its neighbour; the storage the decompiler
actually assigns, read out of the SSA form by
[`BoaArgTrace`](../ghidra/scripts/BoaArgTrace.java), puts the filename buffer at
`sp-328` in a 544-byte frame with the next used slot at `sp-228`. **100 bytes of
room for a ~47-character format.** No overflow. Third time in this project that a
decompiler-derived number was the thing that was wrong.

## Provenance, per call site — added in W04

The census above says *where*. It does not say *what arrives*, and W03 answered
that by decompiling handlers one at a time, which does not scale past the few
that were read.
[`BoaArgTrace.java`](../ghidra/scripts/BoaArgTrace.java) now walks the
decompiler's SSA form backwards from every sink call inside a handler and reports
each argument as a literal, a stack slot with its frame offset, a global, or a
**request parameter with its name**:

| | V2.1.2 | V3.4.0 |
|---|---|---|
| sink call sites inside handlers | 304 | 281 |
| handlers reached by a request parameter | 39 | 30 |

Reports: [`reports/ghidra-argtrace-2.1.2.json`](../reports/ghidra-argtrace-2.1.2.json),
[`reports/ghidra-argtrace-3.4.0.json`](../reports/ghidra-argtrace-3.4.0.json).

It confirmed entries 1 and 2 independently of the hand reading — `form_formWsc`
comes back with exactly `localPin`, `peerPin`, `targetAPSsid` in both builds —
and it found the thing hand-reading had missed: the `submit-url` tail idiom
repeated across 34 handlers, which is
[`submit-url-overflow.md`](submit-url-overflow.md) and accounts for four of this
model's 2025 CVEs at once.

**Three bugs in that tracer were caught by disagreement, not by its own
self-check.** All three are recorded at the end of `submit-url-overflow.md`; the
short version is that a check which never fires never fails, and what caught
every one was comparing the two builds against each other.
